DAILY_SUMMARY BUG FIX - IMPLEMENTATION SUMMARY
============================================
Date: 2026-02-04

PROBLEM
--------
The DAILY_SUMMARY trigger was potentially posting for the wrong CST date because:
1. test_* games could become the "earliest" game, shifting summary time to wrong window
2. Trigger firing was based only on scheduled_time_utc, not CST date
3. Runner did not validate payload.date against current CST date before firing


CHANGES APPLIED
---------------

1. worker/unified_runner.py (+51 lines)
   - Added `json` import
   - Added `_safe_payload_date()` method to extract date from payload (dict or JSON string)
   - Added `_should_process_trigger()` method to guard DAILY_SUMMARY firing
     * Only processes DAILY_SUMMARY when payload.date == current_date_cst
     * Skips with warning if payload date is missing
     * Logs skip reason when payload date doesn't match current date
   - Modified `run_once()` to call `_should_process_trigger()` before processing

2. worker/scheduler.py (+13 lines)
   - Added `real_games` filter to exclude test_* games
   - Modified DAILY_SUMMARY scheduling:
     * Uses `real_games` for earliest game calculation
     * Uses `real_games` for payload construction
     * Falls back to all games if no real games exist
   - This ensures test_* games never affect DAILY_SUMMARY timing or content

3. scripts/start_automation.sh (+19 lines, -7 lines)
   - Added `DATE_ARG` parameter (default: 'today')
   - Changed from `worker.runner` to `worker.unified_runner`
   - Updated process name checks for unified_runner
   - Added Date: $DATE_ARG to status output

VERIFICATION

✓ _should_process_trigger() properly filters by CST date
✓ test_* games are filtered from DAILY_SUMMARY payloads
